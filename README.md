# Aswan Skills Retention Experiment

A Flask application for the **refresher offer × changed task requirements** experiment. This replaces the hiring-vignette concept. Participants actually perform fictional booking tasks. No real employers, customer data, jobs or payments are involved.

Read **START_HERE.txt** first. The app is for a small supervised feasibility pilot; it is not evidence of annual depreciation or labour-market effects.

## 1. Put the code on GitHub

Create a **new repository**, for example `aswan-skills-pilot`. Upload the files in this folder, including the **templates/** and **static/** directories. The repository root must contain `app.py`, `tasks.py`, `requirements.txt` and `render.yaml`.

Do not overwrite your previous loan experiment. Do not upload `instance/`, credentials, response CSVs or invitation links. `.gitignore` protects local files when using Git, but manual browser uploads must also exclude them.

## 2. Deploy on Render

Use **New > Blueprint**, connect the repository and apply `render.yaml`. It defines a free web service and a separate PostgreSQL database. Use the same region for both if Render asks. Confirm any charges before selecting a different plan.

Set the prompted values:

| Setting | Value |
|---|---|
| `ADMIN_PASSWORD` | Your private password, at least 12 characters |
| `STUDY_CONTACT` | Your approved researcher contact information |
| `SECRET_KEY` | Automatically generated by the blueprint; keep it stable |
| `DATABASE_URL` | Automatically connected to the blueprint database |
| `LIVE_RECRUITMENT` | Initially `false` |

The build command is `pip install -r requirements.txt`.
The start command is `gunicorn 'app:create_app()' --bind 0.0.0.0:$PORT --workers 1 --threads 4 --timeout 60`.
The health-check path is `/health`.

If using **New > Web Service** instead, create PostgreSQL separately and enter its connection string as the secret `DATABASE_URL`. Generate a random secret key of at least 32 characters and add the other settings above. The app deliberately refuses SQLite when running on Render. No repository edit should contain a database password.

**Storage matters:** Render free web services have ephemeral local files. Free Render PostgreSQL currently expires after 30 days and lacks managed backups. Download every export regularly and choose a database retention arrangement sufficient for the study. CSVs support analysis but are not a full database restore backup. Ask your hosting provider for a proper PostgreSQL backup/restore process before any main study. Recheck current terms at https://render.com/docs/free.

## 3. Test without waiting seven days

Open `https://YOUR-APP.onrender.com/admin`, sign in, and create **12 TEST invitations**. This generates three assignments per arm in a randomized block-balanced batch. Save all links immediately: plaintext invitation tokens are shown only on that page and cannot be recovered from stored hashes.

Send one link per tester; do not reveal assignments. A token is a private bearer link and can resume the same participant from a different browser. It is not an identity-verification system and must not be shared. The application sends no invitations or reminders itself.

Follow the sequence:

1. Consent and background.
2. Common tutorial and two practice questions, with feedback.
3. Eight baseline questions, without answer feedback.
4. Return page. Refresher-assigned testers can open both practices immediately.
5. Click follow-up when ready. Everyone completes eight original-task retention questions first.
6. The application then reveals stable or changed work instructions, followed by eight work questions.
7. Debrief and completion.

Non-refresher participants have no practice buttons. All TEST participants can start follow-up immediately; use those links only for internal testing. TEST and LIVE exports are separate.

## 4. Real pilot schedule

Before research recruitment, set the approved consent wording and contact, validate the Arabic instructions with participants, obtain the required institutional review, and freeze tasks and the analysis plan. Then set `LIVE_RECRUITMENT=true` and redeploy. Create a new LIVE batch.

Times are relative to each participant's **baseline completion**, in UTC:

- First refresher opportunity: opens 48 hours later.
- Second: opens 96 hours later.
- Both close at 168 hours, or once follow-up begins.
- Follow-up: opens 168 hours later; no upper deadline is enforced.

Practice can be resumed while still inside its window. Each opportunity has four new cases and can be completed once. Participants may decline. Record actual attendance and time gaps; analyse the offer, not only those who take it up. If a participant starts practice then returns after its window, the unfinished records remain in the export and the app returns them to the follow-up page.

Manually send the same scheduled neutral return reminders to all arms. Do not send task instruction to control participants. Contact lists belong in a separate protected file. The app has no automated messaging feature.

## 5. Task definitions

### Original task

Compute nights × nightly rate + 50 EGP service fee, with a 100 EGP discount for stays of four nights or more. Choose among four totals. Numbers and option order are seeded per participant/phase/round and remain unchanged on refresh.

### Changed task

The fictional system supplies the total. Participants choose among four actions based on two new checks: prepaid bookings need payment evidence; guests must not exceed room capacity. Action classes (no issue, payment issue, capacity issue, both issues) each appear twice in eight rounds.

The new task is deliberately a different demand on skills. Its effect can include instruction novelty, switching costs, and task difficulty. It is **not a pure measure of real-world skill obsolescence**. Equal chance levels do not establish equal difficulty. Validate task difficulty and relevance before a larger trial. The retention test is administered **before** changed instructions are revealed, to distinguish retained old-task ability from adaptation. That common retention test itself can prime old skills and is part of this protocol.

The displayed protocol includes bilingual wording. Have Arabic speakers and intended workers review comprehension and equivalence before live use; this is not a validated psychometric instrument. Set real study-specific contact and consent information in `templates/consent.html` as required by your institution. The application does not collect legal names, ID documents or actual employer names.

## 6. Exports

At `/admin`, download all three LIVE exports and store them securely:

- **participants**: one record for every invitation, including no consent, partial completion, assignment, baseline time and debrief.
- **attempts**: one row per displayed task, including unanswered tasks, full task definition, response, correctness and server elapsed time. `round` is zero-based. `task_json` contains the answer key for analysis, but the server never sends its `answer` field into the participant task page.
- **summary**: one row per invited participant, assignment indicators and each phase's completed count, accuracy and total elapsed seconds. Phase accuracy is populated only when all expected tasks are answered; partial counts remain visible. Missing scores are not zero. `retention_change` is retention accuracy minus baseline accuracy, not an annual depreciation rate.

Elapsed time is wall-clock time since first display and includes inactivity, refreshes and disconnections. It is not a pure processing-speed measurement. Prespecify handling of long inactive gaps and device changes. Unique study IDs and dates remain potentially identifying; protect de-identified exports accordingly. CSV formula-like text is escaped on export.

Use `analyse_pilot.do` with `summary_live.csv` in Stata for descriptive counts and arm summaries. It does not present a tiny pilot as definitive causal evidence. The raw attempt export preserves data needed for a later prespecified analysis.

## 7. Local use on Windows

Install Python 3.11 or newer. Extract the package, open Command Prompt in its folder and run:

```bat
py -m venv .venv
.venv\Scripts\activate
python -m pip install -r requirements.txt
python setup_local.py
python app.py
```

Open `http://127.0.0.1:5000/admin`. Your randomly generated local admin password is in `instance/local_config.json`. Keep that file private. The development server is for local testing only. Local records use `instance/study.db` and are not uploaded automatically to Render. Use separate TEST invitations after deploying. PostgreSQL is used on Render.

For automated checks:

```bat
python -m pip install -r requirements-dev.txt
python -m pytest -q
```

## 8. Research and deployment limits

- Ten to fifteen participants are a feasibility pilot, not a powered main study. Repeated tasks do not multiply the number of independent people.
- Assignment is randomized within blocks of four **inside each invitation batch**. Make a single batch for the planned pilot; creating many tiny batches can leave allocation imbalanced. People who do not use invitations can still create imbalance among responders; report it.
- There is no random assignment to actual job loss, unemployment duration or real technology adoption.
- The app is versioned `skills-retention-1.0`. Freeze deployment during collection. If you change tasks, schedules or scoring, change the version and define a new protocol. Existing records with an unmatched version are blocked from continuing, rather than silently receiving new tasks. Never use this blocking mechanism as a substitute for a migration plan during active data collection.
- One person can share their link; technical tokens alone cannot prevent impersonation. Track recruitment separately without adding identifying details to the analysis file.
- No data deletion button is included. Explain approved withdrawal procedures and arrange researcher-managed record deletion using study IDs before live recruitment.
- This package has been tested locally. It has not been deployed to your GitHub/Render accounts or tested against your eventual hosted PostgreSQL instance. Run TEST sessions and verify exports after deployment before opening live recruitment.
